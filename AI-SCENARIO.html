一、背景：AI 应用建设正在改变数据访问的基本假设

企业级 AI 应用（智能问数 ChatBI、知识库 RAG、Agent 工作流、研发/办公 Copilot）与传统应用最大的差异在于：数据访问的发起者从「确定性的代码」变成了「概率性的模型」。传统应用的每一条 SQL 都由工程师写死、经过评审；而 AI 应用中的 SQL 由 LLM 现场生成，其内容不可预测、不可穷举、且可被提示词注入操纵。

这意味着过去「应用持有数据库账号 + 代码内控权限」的模式在 AI 场景下完全失效——你无法对一个会自己写 SQL 的系统做代码评审。治理必须从应用层下沉到数据访问层，在 SQL 真正落到数据库之前，由一个独立、强制、可审计的中间层完成校验与改写。这正是 Aegis 的定位。

一句话必要性：没有治理代理层的 AI 应用，等价于给一个「不可控的实习生」发放了生产数据库 root 密码。Aegis 把它换成「带工牌、有权限边界、全程录像」的受控访问。

二、必要性论证：五大风险 × 平台对策

风险 1 · 凭据失控：AI 应用持有高权数据库账号

LLM 应用的提示词注入（Prompt Injection）已被证明可诱导 Agent 执行任意工具调用。若 Agent 直连数据库，一次注入即等于交出整库。凭据还会随代码仓库、日志、配置中心扩散。

对策（已落地）· 账号隔离

AI 侧只持有平台签发的 JWT / MCP API Key，可随时吊销、轮换、缩权；后端数据库使用受限服务账号（如 aegis_svc 仅授权 dh_demo.*），root 等真实凭据永不出平台。

风险 2 · 权限语义缺失：数据库账号表达不了业务边界

MySQL/PostgreSQL 的原生账号体系是「库/表」粒度的，无法表达「销售只能看自己大区」「租户 A 的 Agent 只能查租户 A 的数据」这类业务语义。为每个业务身份建 DB 账号在运维上不可行。

对策（已落地）· 表/行/列三级治理

角色 × 数据源 × 表的操作授权（默认拒绝）；行策略以 :attr 占位符从 JWT 属性代入（如 tenant_id = :tenant），查询时注入为派生表；列级脱敏在结果层强制执行。业务边界在平台配置，一处生效、全渠道一致。

风险 3 · 幻觉 SQL 无兜底：提示词约束不可信

NL2SQL 可能生成无 WHERE 的 DELETE、笛卡尔积 JOIN、跨越授权范围的查询。「请只查询 orders 表」这样的提示词约束对被注入或幻觉中的模型没有强制力。

对策（已落地）· SQL 解析级强制校验

每条 SQL 先经语法树解析 → 表级操作校验 → 行策略重写 → 列脱敏，治理发生在引擎层而非提示词层，模型说什么不重要，能执行什么由平台决定。语句类型白名单（仅 SELECT/INSERT/UPDATE/DELETE），DDL 天然被拒。

风险 4 · 合规不可追溯：AI 查了什么无人知晓

《数据安全法》《个人信息保护法》与等保 2.0 均要求数据访问留痕可审计。AI 应用的访问行为高频、机器化、语义不可预知，出现数据泄露事件时若无法回答「哪个 Agent 在何时查了哪些数据」，责任无法界定。

对策（已落地）· 全量审计

audit_logs 对 ok / denied / error 三态全留痕，记录用户、渠道（dataapi/mcp）、原始 SQL、治理重写后 SQL、返回行数、耗时；管理台可按用户/数据源/状态/渠道过滤检索。

风险 5 · 重复建设：每个 AI 应用各自接数据

企业往往同时上多个 AI 项目，各自做数据接入、各写一套权限与脱敏逻辑，成本翻倍、口径不一，且安全水位取决于最薄弱的那个项目。

对策（已落地）· 统一数据供给

DataAPI（REST）服务传统应用与数据产品，MCP（Streamable HTTP）服务 AI Agent，两条通道共享同一治理引擎与审计流水。新 AI 应用接入 = 发一个 Key + 配一组权限，分钟级完成。

三、典型 AI 场景映射

📊 智能问数 / ChatBI业务人员自然语言提问 → LLM 生成 SQL → 必须经 Aegis 强制治理后执行。行策略保证「问自己能看的数」，列脱敏保证敏感字段不进对话上下文。
🤖 Agent 工作流多步骤 Agent（报表生成、对账、运营巡检）通过 MCP 工具链取数。API Key 映射到低权服务身份，限流与行数上限防止失控循环拖垮生产库。
📚 知识库 RAG 增强RAG 应用需要实时结构化数据补充答案（库存、订单状态）。DataAPI 提供受治理的查询接口，避免向量库之外再开一条「裸连」通道。
💻 员工 Copilot面向内部员工的助手按登录者身份（JWT attrs）取数，同一个问题不同人得到各自权限内的答案——权限跟人走，而非跟应用走。

四、功能扩充规划（面向 AI 场景）

P0① AI 数据供给增强

功能说明状态
MCP resources / prompts把数据源目录、表结构语义卡片作为 MCP resources 暴露；提供「如何安全查询」的 prompts 模板，减少 Agent 摸索成本规划
Schema 语义描述为表/列维护业务含义注释（「amount = 含税订单金额，单位元」），随 describe_table 下发，显著提升 NL2SQL 准确率规划
NL2SQL 安全网关平台内置「自然语言 → SQL → 治理校验 → 执行」端到端接口，企业无需在每个应用重复实现规划
语义指标层统一定义核心指标（GMV、活跃用户）的计算 SQL，AI 引用指标而非现场编 SQL，根治口径漂移远期

P0② AI 行为治理

功能说明状态
结果行数上限按角色配置 max_rows，超限自动截断并在审计中标记，防全表拖库进 LLM 上下文规划
查询超时熔断按数据源配置执行超时，慢查询主动取消，保护生产库规划
限流与配额按用户/Key 配置 QPS 与日查询量，防 Agent 失控循环规划
高危语句拦截无 WHERE 的 UPDATE/DELETE 直接拒绝（可配置豁免）；语句类型白名单已具备部分落地
查询成本预估执行前 EXPLAIN，预估扫描行数超阈值直接拒绝并提示优化远期

P1③ 安全合规升级

功能说明状态
动态脱敏掩码显示（138****0001、邮箱域保留）替代整列剔除，兼顾可用性与安全规划
分级分类标签为列打 PII/敏感/内部/公开 标签，策略按标签批量下发，对齐数据安全分级要求规划
审计升级关联 AI 会话 ID（一次对话的多条查询串联）；异常行为规则告警（高频 denied、深夜批量导出）规划
身份体系对接SSO / LDAP / OAuth2 对接企业统一身份；API Key 到期与轮换机制规划

P1④ 平台化与生态

功能说明状态
多数据源扩展PostgreSQL（驱动已内置，待端到端验证）；达梦、OceanBase、TiDB 等信创/分布式库部分具备
读写分离路由AI 查询默认路由只读副本，与交易流量物理隔离规划
低代码 DataAPISQL 模板 + 参数定义一键发布为受治理的 REST 接口，供无 SQL 能力的应用消费规划
云原生部署K8s Helm Chart、多副本（控制面迁 PostgreSQL）、Prometheus 指标、OpenTelemetry 链路规划

五、实施节奏建议

  1. 近期（阶段 2 收尾 + 阶段 3 启动）：行数上限 + 查询超时 + 限流（②中三项，改动集中在 proxy 层，成本低、对 AI 上生产是硬前提）；MCP resources + Schema 语义描述（①中两项，直接提升 Agent 取数体验）。
  2. 中期：动态脱敏与分级分类标签（③）、PostgreSQL 端到端验证与读写分离路由（④）。
  3. 远期：NL2SQL 安全网关与语义指标层——待前两层稳定后，把平台从「安全通道」升级为「AI 数据服务中台」。
投入产出判断：P0 两组能力（供给增强 + 行为治理）合计约 6–8 个功能点，均在现有单二进制架构内演进、不引入新组件；完成后 Aegis 即可支撑 ChatBI 与 Agent 工作流安全上生产，是性价比最高的下一步。
